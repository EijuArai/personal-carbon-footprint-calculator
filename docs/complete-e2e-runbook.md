# E2E Runbook

## Scope

This runbook documents the managed local complete E2E workflow for the Green
Reputation repository.

It covers:

- startup prerequisites
- generated env and signer materials
- one-command orchestration
- browser E2E execution
- current known blockers
- dev-only safety warnings

Use the workspace-specific runbooks for component-level details.

## Managed Workflow

The local complete E2E workflow is rooted at `scripts/local-e2e/up.sh`.

Repository root commands:

```bash
bash scripts/local-e2e/up.sh
bash scripts/local-e2e/status.sh
bash scripts/local-e2e/down.sh
```

The startup workflow owns:

1. validator reset
2. managed keypair creation or reuse
3. signer funding
4. program deploy
5. protocol bootstrap
6. backend startup
7. worker startup
8. frontend startup
9. readiness checks

## Fixed Endpoints

- frontend: `http://127.0.0.1:4173`
- backend: `http://127.0.0.1:3000`
- Solana RPC: `http://127.0.0.1:8899`
- Solana WS: `ws://127.0.0.1:8900`

These values are fixed by the current orchestration contract and should be used
for local troubleshooting.

## Generated Materials

The workflow stores managed state under `.local-e2e`.

Important paths:

- `.local-e2e/keys/admin.json`
- `.local-e2e/keys/verifier.json`
- `.local-e2e/keys/metadata-authority.json`
- `.local-e2e/keys/mint-authority.json`
- `.local-e2e/keys/user.json`
- `.local-e2e/env/backend.local-e2e.env`
- `.local-e2e/env/frontend.local-e2e.env`
- `.local-e2e/logs`
- `.local-e2e/backend/green-reputation.sqlite`

The managed keys persist across runs. Runtime state, logs, ledger state, and env
files are regenerated by `up.sh`.

## Failure Triage

### Stack Does Not Start

Run:

```bash
bash scripts/local-e2e/status.sh
```

Then inspect:

- `.local-e2e/logs/backend.log`
- `.local-e2e/logs/worker.log`
- `.local-e2e/logs/frontend.log`
- `.local-e2e/logs/validator.log`

### Browser Submission Fails With `Failed to fetch`

Check backend cross-origin behavior first.

```bash
curl -i http://127.0.0.1:3000/v1/crypto/public-key -H 'Origin: http://127.0.0.1:4173'
curl -i -X OPTIONS http://127.0.0.1:3000/v1/dev/auth/ingest-token -H 'Origin: http://127.0.0.1:4173' -H 'Access-Control-Request-Method: POST' -H 'Access-Control-Request-Headers: content-type'
```

If those responses do not include the expected cross-origin headers, the browser
will block the request and Playwright will never reach backend ingest logic.

### Jobs Never Complete

Current queue observability is internal-only.

Useful checks:

```bash
tail -n 200 .local-e2e/logs/worker.log
tail -n 200 .local-e2e/logs/backend.log
```

Do not treat `GET /v1/jobs/:jobId` as a stable public UX surface.

## Dev-Only Safety Warnings

The managed local complete E2E workflow contains deliberate shortcuts that are
acceptable only for local development.

- `POST /v1/dev/auth/ingest-token` is a dev-only auth bridge
- `.local-e2e/env/frontend.local-e2e.env` injects signer material into browser
  runtime via `VITE_*`
- `GET /v1/jobs/:jobId` is currently unauthenticated and sequentially enumerable
- the default JWT secret must never be used for deployment

Do not:

- reuse local-E2E env files in shared environments
- expose the local frontend runtime outside a trusted local machine
- treat the current browser signer harness as a production design
- document the internal job route as a public contract

## Recommended Execution Pattern

1. Run workspace quality gates first.
2. Start the managed local stack.
3. Confirm stack readiness.
4. Run Playwright.
5. If Playwright fails, check whether the failure is a browser or network
   boundary issue, a backend queue problem, or an on-chain state problem.
6. Shut the stack down when done.

Suggested command sequence:

```bash
cd solana && anchor test
cd ../backend && npm test
cd ../frontend && npm run quality
cd .. && bash scripts/local-e2e/up.sh
bash scripts/local-e2e/status.sh
cd frontend && npm run e2e
cd .. && bash scripts/local-e2e/down.sh
```
